# Сервер Recap: что есть и что добавлять по мере роста

_Октябрь 2026. Короткая версия: Kafka, Argo и Kubernetes не нужны — ни сейчас,
ни на десятках тысяч пользователей. Нужны три шага, и каждый — только когда
упрёмся в конкретный предел._

## Что есть сейчас

| Часть | Что делает | Почему так |
|---|---|---|
| **Приложение** (SwiftUI + SwiftData) | всё обучение: карточки, расписание, тренажёры, карта | работает без сети; сервер не нужен для занятий |
| **Cloudflare Workers** | прокси к ИИ, подписка, промокоды, лимиты, бэкапы | без серверов и Kubernetes: сам масштабируется по миру, платишь за запросы |
| **D1** (SQLite у Cloudflare) | устройства, подписки, квоты, каталог, бэкапы кусками | одна база, миграции в `backend/migrations` |
| **Anthropic API** | наборы, уроки, разговоры | ключ только на сервере (секрет Workers) |

Сервер почти без состояния: каждый запрос — независимая функция. Поэтому
«масштабировать» его не надо — Cloudflare запускает столько копий, сколько
пришло запросов. Узкие места появятся в хранении, а не в вычислениях.

## Что добавлять и когда

1. **R2 для бэкапов** (аналог S3, без платы за скачивание) — первым делом,
   когда бэкапов станет много. Сейчас снимки лежат в D1 кусками; у D1 предел
   размера базы (10 ГБ), и мегабайтные снимки быстро съедят его у служебных
   таблиц. В D1 останется только список копий, сами файлы — в R2. Туда же
   потом — озвучка и картинки, если появятся.
2. **Queues** (очереди Cloudflare) — когда появится тяжёлая фоновая работа:
   пачкой собрать каталог, обработать большой PDF, рассылка. Это и есть
   «Kafka» нашего масштаба: задание кладётся в очередь, обработчик берёт и
   повторяет при сбое. Kafka нужна, когда десятки сервисов обмениваются
   потоком событий, — это не наш случай.
3. **Durable Objects** — если счётчики лимитов начнут спорить за одну строку
   D1 (тысячи запросов в секунду от одного устройства не будет, но от всех
   вместе — общий дневной потолок помощника). Объект держит счётчик в памяти.

Позже, если понадобится сложная аналитика и отчёты по всем пользователям, —
Postgres (Neon или Supabase) через Hyperdrive рядом с D1, а события
использования — в PostHog (см. задачу аналитики), а не в свою базу.

## Чего не надо

- **Argo (Argo CD / Workflows)** — инструменты для Kubernetes. Кластера у нас
  нет и не нужно: деплой — `wrangler deploy` из GitHub Actions.
- **Kafka** — см. выше: очереди Cloudflare закрывают фоновые задания.
- **Свой сервер на VPS** — придётся самим следить за обновлениями, бэкапами,
  нагрузкой и безопасностью. Workers дают это готовым.

## Что уже готово для роста

- API версионирован (`/v1/...`) — старые версии приложения не ломаются.
- Новые поля в запросах необязательны (`target`, `requestId`), сервер
  понимает и старые запросы.
- Повтор запроса после обрыва не списывает квоту дважды (`deck_requests`).
- Лимиты на устройство и на весь сервер — защищают бюджет на ИИ.
- Android позже ходит в тот же API; логика приложения — в `Core/`,
  её переносят на Kotlin один раз.
